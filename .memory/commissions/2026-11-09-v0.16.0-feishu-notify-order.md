## 1. 背景：这次要修的真实问题

用户在帖文页点「提取并概括」后，**任务还在跑的时候**把同一帖的短链贴进「添加素材」框。面板先存 `pendingGivenUrl`，任务结束后才发 `XHS_AI_RELINK`。但飞书自动推送发生在后台生成完成的那一刻，早于 relink：

```text
生成：renderSummary(长链) → pushFeishu(长链) → 返回结果 → 面板显示(长链)
补链：面板 pending → 任务完成后 relink → renderSummary(短链) → 面板/历史(短链)
飞书：保持长链
```

根因不是渲染，是**发送时机**：

- 生成时只渲染一次文本并立刻推送：`ai-pipeline.js:819`（`text: renderSummary(structured, payload)`），`service-worker.js:650`（`pushFeishuNotification(publicResult.text, ...)`），合并同理 `service-worker.js:995`。
- 补链接走 `relinkResult`（`service-worker.js:1097`），只重渲染、更新历史，**不调用模型，也不推送飞书**；提示语是「链接已更新（未重新推送飞书）」（`service-worker.js:1048`）。
- 任务进行中贴链接：`panel.js:1140` 写 `pendingGivenUrl`，完成后 `panel.js:1179` 才 relink。
- 结果已存在后贴链接：`panel.js:1145-1159` 直接 relink，同样不重推。
- 测试甚至固定了这个行为：`tests/panel.test.cjs:1328` 断言任务中贴链接时 `givenUrl` 是 `null`，`tests/panel.test.cjs:1352-1354` 断言完成后才 relink。

用户确认采用 **方案 1+2**：

1. 生成中贴入的链接，等链接归位后再推送最终文本，**只发一条**；
2. 结果已经推送过之后再补链接/编辑，不自动重发第二条，但必须**明确标记飞书里是旧版本**，并提供**一键重发**。

同时修三个顺带发现的问题：

- 先贴链接、还没提取时，提示错写成「链接已更新（未重新推送飞书）」。
- `notification` 不随补链接/编辑更新，历史里也带着旧的已发送状态，提示误导。
- 合并结果同样有时序问题（合并运行中改条目链接，飞书仍发旧链接）。

以及合并的同一类问题：合并结果已经发送后再改链接/编辑，也要有旧版本标记和一键重发。

## 2. 目标行为（验收口径）

### 2.1 单条：任务进行中贴链接

1. 后台生成完成后、推送飞书前，先问面板：这个页签本次生成所用的 `givenUrl` 之外，是否还有一个更新的待补链接？
2. 有 → **不推送**，结果上的 `notification = { status: "deferred" }`，正常返回结果；面板完成 relink 后，用**最终 `result.text`** 调后台推送一次。
3. 没有（或待补链接与本次 `givenUrl` 相同）→ 照旧立即推送。
4. 最终效果：面板文本 = 飞书文本；短链；**每个生成任务只产生一条飞书消息**；状态行说明「链接已更新，并已推送到飞书」。
5. 如果面板在延迟推送完成前被关闭：不阻塞结果生成；历史里的 `notification` 保持 `deferred`，用户之后可在结果/历史里点飞书图标手动发送。此边界写进任务记录「遗留问题」。

### 2.2 单条：结果已存在后再补链接 / 手工编辑

1. 不自动重发第二条（webhook 无法改/撤消息，重复消息不可接受）。
2. 每次成功推送都把**实际发送的文本**写进 `notification.sentText`。
3. 当前结果文本（`result.text`，trim 后比较）与 `notification.sentText` 不一致，或 `notification.status === "deferred"` 时：
   - 结果卡显示一条常驻提示：`飞书里仍是旧版本，点飞书图标重发当前内容。`（deferred 时：`这条概括还没有推送到飞书，点飞书图标发送当前内容。`）
   - 飞书图标加 `data-stale="true"` 和红点，`title` / `aria-label` 改为 `飞书里仍是旧版本，点击重发`（deferred：`还没有推送到飞书，点击发送`）。
4. 点图标发送当前文本；成功后后台更新 `notification`（`sentText`、`sentAt`、`channel`）并写回历史/工作流快照，提示和红点消失。
5. 手工编辑结果框同理：输入时实时刷新标记；改回已发送文本则标记消失。
6. 旧数据没有 `sentText` 时按「无法判断」处理，不显示旧版本标记；不要报错。

### 2.3 合并结果

1. 合并任务运行中，用户改了清单条目的链接（含清空）→ 面板记一个「本次合并期间链接有改动」标记。
2. 后台合并完成、推送前同样查询面板；有改动 → `notification = { status: "deferred" }`，不推送。
3. 面板收到结果后：
   - 若标记为真，先复用现有 `XHS_AI_MERGE_RERENDER` 用当前清单重渲染（只有 `itemIds` 集合未变时才允许原地重渲染；`rerenderMergeResult` 已有这个保护）。
   - 用重渲染后的最终文本推送一次，更新 `notification`；只发一条消息。
   - 若重渲染返回 `unchanged`（条目集合变了），保留原结果并推送原文本，同时在「添加素材」反馈里提示：`合并条目已变化，本次合并结果未包含新的链接。`
4. 合并结果已发送后再改链接/编辑 → 与 2.2 相同的旧版本标记 + 一键重发。
5. 合并任务运行中贴入的链接如果属于当前页签但不属于清单，按单条规则处理，不影响合并。

### 2.4 先贴链接、还没提取

- 提示从「链接已更新（未重新推送飞书）。」改为：`已记下链接，提取时会带入。`
- 如果同一次操作里清单条目也被实际更新，保留正常的「链接已更新。」提示；不要同时说两件事。
- 提取时仍把 `pendingGivenUrl` 带进生成请求（现有行为，不变）。

### 2.5 补链接本身的语义（不变）

- 只写 `source.givenUrl`，不改 `source.url`；不重新采集、不调用文字/图片模型、不新增历史条目、不重推（除非是 2.1/2.3 的延迟推送补偿）。
- 保留 `renderedText` 和「手工编辑只替换后缀/旧链接、找不到时 kept」的全部现有逻辑。
- 合并结果只有 `itemIds` 未变时才原地重渲染。
- 截图帖文的补链接、`givenUrlVerified` 语义不变。
- 截图识别流程（`XHS_AI_SUMMARIZE`，`service-worker.js:1240`）仍在生成后立即推送；截图不参与延迟推送（它的链接在创建时已确定）。

## 3. 推荐实现方案

可以按下面的消息与状态实现；如果发现更小且行为等价的方案，先在最终报告里说明，不要静默改行为。

### 3.1 后台 → 面板的查询

新增消息（后台 `chrome.runtime.sendMessage` 发给扩展页面）：

```js
{ type: "XHS_AI_QUERY_PENDING_LINK",
  kind: "page" | "merge",
  tabId?: number,            // kind = page
  pageSessionId?: string,    // kind = page
  givenUrl?: string }        // kind = page，本次生成实际用的 givenUrl，可为空
```

面板监听并**同步** `sendResponse({ pending: boolean })`：

- `kind = "page"`：只处理自己拥有的 `tabId` 且 `slot.context.pageSessionId === message.pageSessionId` 的页签；不是自己的页签返回 `false` 且**不响应**（避免多窗口时别的面板抢先答 false）。自己的页签返回：
  `pending = Boolean(slot.pendingGivenUrl && slot.pendingGivenUrl.trim() !== (message.givenUrl || "").trim())`。
- `kind = "merge"`：只在自己 `tasks.has("merge")` 时响应，返回 `Boolean(mergeLinkDirty)`；没有合并任务时不响应。
- 必须同步响应，不能 `await`；响应后 `return false`。

后台封装：

```js
async function panelHasPendingLink(target) {
  // chrome.runtime.sendMessage + 1500ms 超时；无响应/异常 → false（照旧立即推送）
}
```

后台只在 `hasFeishuSettings(config, secrets)` 为真时查询；没配飞书就不查、不推送。

### 3.2 延迟推送与状态

- `notification.status` 扩展为 `"sent" | "failed" | "deferred"`。
- `pushFeishuNotification` 成功时增加 `sentText: text`（实际发送的 trim 后文本）。
- `summarizePayload` 增加可选参数（建议 `options.shouldDeferNotify`）：
  - 有 Feishu 配置且 `shouldDeferNotify()` 返回真 → 不调用 `pushFeishuNotification`，`notification = { status: "deferred" }`；进度提示改为「链接更新后自动推送飞书」或直接跳过 notification 进度，不要显示「正在推送飞书」。
  - 否则按现状推送。
- `summarizePagePayload` 传入查询回调：`kind: "page"`、`tabId`、`pageSessionId`、`givenUrl = payload.source?.givenUrl || ""`。
- `summarizeMergeBasket` 传入查询回调：`kind: "merge"`。
- `XHS_AI_SUMMARIZE`（截图单条）不传回调，保持立即推送。

新增面板 → 后台消息，并加入 `EXTENSION_PAGE_MESSAGES`：

```js
{ type: "XHS_AI_NOTIFY_FEISHU_RESULT",
  text: string,
  historyId?: string,
  tabId?: number,
  pageSessionId?: string,
  kind: "single" | "merge" | "screenshot" }
```

后台处理：

1. 校验 text 非空、长度 ≤ 20000（与手动发送一致）。
2. `[config, secrets]`，未配置 → 返回 `{ ok: true, notification: null }`（面板清掉 deferred 状态即可）。
3. `notification = await pushFeishuNotification(text, config, secrets)`（成功带 `sentText`）。
4. 更新历史条目（按 `historyId`）与工作流快照（按 `tabId` + `pageSessionId`）里的 `result.notification`。
5. 返回 `{ ok: true, notification }`；发送失败也按 `pushFeishuNotification` 的 `{status:"failed", error}` 返回，不要抛出成任务失败。

### 3.3 手动发送也记录版本

`XHS_AI_SEND_FEISHU` 增加可选 `historyId`、`tabId`、`pageSessionId`、`kind`。发送成功后：

- 返回 `notification = { status: "sent", channel, sentAt, sentText: text }`。
- 同样更新历史/工作流快照里的 `result.notification`。
- 不传上下文的旧调用保持可用（只有 text 也能发）。

### 3.4 工作流快照更新不要覆盖面板编辑

手动发送时结果框里的文本可能已被用户编辑（编辑只存在面板当前会话，不写工作流快照）；延迟推送时结果文本是最终文本，但为了一致也建议同样处理。更新 `result.notification` 时：

- 更新 `chrome.storage.session` 里的工作流快照（供面板重开后读取），**不要广播** `XHS_AI_WORKFLOW_STATE` 覆盖面板当前结果文本；
- 历史条目照常更新；
- 面板收到响应后自己更新本地 `result.notification`。

可以沿用 `workflowStateWrite` 串行链，写一个只改 `result.notification` 的小 helper。注意 `updateWorkflowState` 会广播，手动发送路径不要直接用它。

### 3.5 面板流程

新增 `finalizeDeferredFeishu(target)`（target 为 `"tab"` 或 `"merge"`）：

- 取当前结果；`notification.status !== "deferred"` → 直接返回。
- 用最终 `result.text` 发 `XHS_AI_NOTIFY_FEISHU_RESULT`。
- 成功：把返回的 `notification` 写回结果；更新状态（见 3.6）。
- 失败/消息异常：把 `notification` 设为 `{ status: "failed", error }`，状态显示推送失败；不要影响已经生成的结果。
- 更新本地面板（`slot.result` / `mergeSlot.result`），按焦点重渲染。

调用点：

- `runFullWorkflow`：`await settlePendingLinkAfterWorkflow(...)` 之后、`finally` 移除任务之前调用 `finalizeDeferredFeishu("tab")`。
- `regenerateActiveTab`：同样在 settle 之后调用。
- `settlePendingLinkAfterWorkflow` 需要能让调用方知道「本次是否真的发生了 relink」（返回值，或调用前比较 pending 与 usedGivenUrl），`finalizeDeferredFeishu` 据此选择状态文案。
- 如果 settle 的 relink 失败（pending 保留、面板已提示错误）：`finalizeDeferredFeishu` 仍按当前 `result.text` 推送，避免简报丢失；当前显示文本就是发送文本，符合所见即所发，同时保留 relink 错误提示。
- `runMergeSummarize`：
  - 开头 `mergeLinkDirty = false`；
  - `setBasketItemLink`（`panel.js:1260`）在 `tasks.has("merge")` 时置 `mergeLinkDirty = true`（在发消息前同步置位）；
  - 收到结果后：若 `notification.status === "deferred"`，先 `if (mergeLinkDirty) await rerenderMergeIfPossible()`，再 `await finalizeDeferredFeishu("merge")`；
  - 若结果已经是 `sent` 但 `mergeLinkDirty` 为真（查询窗口后的极小竞态），只重渲染显示并让旧版本标记生效，不自动发第二条；
  - 最后再写 `mergeSlot.status`。
- `runLinkWorkflow`（新页签链接概括）没有 pending 链路，不需要延迟；如顺手加 `finalizeDeferredFeishu("tab")` 也只能是空操作，可不加。

### 3.6 状态与提示文案

- `completionDetail` 增加 deferred：`概括已生成，链接更新后会自动推送飞书。`
- 延迟推送成功且发生过 relink：`链接已更新，并已推送到飞书。`
- 延迟推送成功但没 relink（待补链接与生成用的相同）：沿用 `概括已生成，并已推送到飞书。`
- 推送失败：沿用 `概括已生成；飞书推送失败：<error>`。
- `RELINK_UPDATED_HINT` 从 `链接已更新（未重新推送飞书）。` 改为 `链接已更新。`
- `RELINK_KEPT_HINT` 保持不变。
- 旧版本/未推送提示放在结果卡动作行下方的新元素 `#feishu-stale-hint`，不要挤进 `#feishu-feedback`（发送成功/失败的反馈仍用原元素）。
- 结果卡不可见时不显示该提示；飞书未配置时隐藏图标和提示。

### 3.7 UI

- `panel.css`：
