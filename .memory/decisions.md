## 早期（日期不详，2026-10 以前）

### 模型 Key 由用户自备

- **决定**：扩展不内置任何 API Key，用户在设置页填写自己的 OpenAI-compatible 接口。
- **理由**：商店合规；避免密钥泄露与费用风险。

### 图片识别与文字概括分开调用

- **决定**：图片模型只负责如实描述和 OCR；内容是否有增量、是否写进概括，由文字模型判断。
- **理由**：串行合并调用对图片多的帖文太慢；职责分开后两边提示词都更好控制。

### 提示词通过书面规则修正，不加示例

- **决定**：输出质量问题通过改写提示词里的规则解决，坚持最小干预、一次只改一处并单独测试。不新增 few-shot 示例，现有示例也考虑移除。
- **理由**：示例容易被模型照抄，让输出变得僵硬。

## 2026-10-28

### 侧边栏改为统一工作区（v0.13.0）

- **决定**：去掉「单条帖文概括 / 多条帖文概括」两个页签，改为「当前帖文 / 添加素材 / 清单 / 结果」四个区块。任何来源得到的帖文都是同一种素材，可以单独概括，也可以随时加入清单合并。
- **理由**：单条还是多条，是素材攒到最后才知道的，不该一开始就让用户选模式。原设计导致两个痛点：概括后补不进短链；已概括的帖文无法直接转入合并。
- **否掉的方案**：保留双页签、只在结果卡片上加「补链接」和「加入清单」。改动小，但界面「两套东西并排」的混乱感不会消失。

### 短链自动识别归位，为此新增 xhslink.cn 权限

- **决定**：只设一个「添加素材」输入框。贴入的链接先解析成帖子 ID，再与当前帖文、清单条目比对：对上了就补链接，对不上就作为新帖打开，解析失败就让用户手动选择，绝不猜。结果卡片和清单条目上的链接框保存时也会校验。
- **理由**：短链本身不含帖子 ID，只靠输入框位置区分意图，用户要自己贴对地方，贴错了插件无法察觉，错链接会直接写进简报。
- **否掉的方案**：按输入框位置区分「补链接」和「新帖」，不加权限。

### 只支持 xhslink.cn，不支持 xhslink.com

- **决定**：短链解析与权限只覆盖 `xhslink.cn`。
- **理由**：用户实际拿到的短链基本都是 `.cn`。

### 补链接不调用模型、不重推飞书

- **决定**：换链接时只改 `source.givenUrl`，用已有的结构化结果重新渲染，并同步历史；不重新推送飞书，状态行注明「未重新推送飞书」。
- **理由**：链接本来就是程序写入的，与模型输出无关；重推会在飞书里产生重复消息。

### 引入 AGENTS.md 与 .memory 任务记录体系

- **决定**：根目录放 `AGENTS.md` 规定 AI 的工作流程；`.memory/` 存放项目上下文、决策日志、待办和每个任务的记录。交付说明就写在任务记录里，不再在根目录建 `DELIVERY.md` 或 `docs/delivery/`。
- **理由**：实现工作交给不同的 AI 会话完成，需要一个随仓库走的长期记忆，避免每次重新摸索或推翻已有决定。
- **配套**：打包改为白名单脚本，确保这些文件不会进入扩展包。

### 补链接不覆盖结果框里的手工编辑（v0.14.4）

- **决定**：结果对象记录 `renderedText`；补链接时若 `text` 已被手工改过，只替换旧的来源后缀或旧链接，两者都找不到就保持用户文本、提示手动修改。历史仍保存程序重渲染的干净文本。
- **理由**：链接是程序写入的，用户改的是正文；整段重渲染会无提示地丢掉用户的编辑。
- **否掉的方案**：继续整段重渲染，只在界面上加“编辑会被覆盖”的警告。

### 打包白名单要有防漏测试

- **决定**：`tests/package.test.cjs` 从 manifest、页面引用、`importScripts` 和 `executeScript` 反查运行时文件，缺一个就让 `npm run check` 失败。
- **理由**：白名单靠人工维护，新增文件时漏加只会在打包后才暴露。

### 任务记录只记里程碑，微调合并归档（2026-10-29）

- **决定**：任务记录只为有分量的版本立档（新行为、新约定、新权限、成批修复）。纯样式或文案微调并入本次会话最近的任务记录，或与相邻小版本合并成一份档案，一个版本一行；被后续版本取代的中间方案（如同一图标多次重画）不留细节，最终形态以 `context.md` 约定和代码为准。
- **理由**：2026-10-28 一天产生 14 份记录，其中 10 份是界面微调，内容与 `context.md` 的约定重复；重新生成图标一个图标写了 4 份。任务记录的价值在决策与验收上下文，不在逐次改动本身。
- **整理**：v0.13.2–0.13.8、v0.14.1–0.14.3 十份合并为 `tasks/2026-10-28-v0.13.2-0.14.3-ui-polish.md`；完整保留 v0.13.0、0.13.1、0.14.0、0.14.4 四份。

### 平台徽标统一：小红书一律红色「小红书」，不再叫「网页」（v0.14.6–v0.14.7）

- **决定**：所有出现平台徽标的位置（当前帖文、任务条、清单、历史列表），小红书固定显示「小红书」并用主题红（`merge-badge-xhs`）；微博橙、截图绿（v0.14.7 由深红改回绿，与小红书红拉开区分度）、合并黑不变。
- **理由**：历史列表里小红书条目曾显示绿色「网页」，与微博「微博」不对等；绿色也与产品主色冲突。用户确认统一为品牌红。
- **否掉的方案**：维持「网页」通称；为小红书另选配色；截图徽标继续用深红。

### 截图证据对齐网页帖：配图文字并入 imageEvidence（v0.15.0）

- **决定**：截图帖文的配图文字不再以 `note.imageText` 裸原文进入证据，由 `buildEvidence` 合成一条与图片模型输出同结构的 `imageEvidence` 条目；是否写入、怎么转述交给写作提示词已有的图片规则判断。
- **理由**：提示词里的图片规则只作用于 `imageEvidence`，裸原文管不到，导致「图片文字为……」整句照搬。证据形态对齐后写作规则只维护一处。
- **否掉的方案**：为截图单独写一份写作提示词。

### 截图原样上传，不缩放不转码（v0.15.0）

- **决定**：删除 `downscaleDataUrl`，截图以原始文件、原始尺寸、原始格式上传；本批 data URL 总长超 32 MB 时提示分批识别，模型拒收时透出接口原始报错并建议拆分。
- **理由**：长边压到 1600px 会把长截图文字压到不可辨，是截图概括质量差的主因之一。
- **否掉的方案**：长截图自动按 2.5 倍宽高比切段（先原样上传观察模型表现，记入 backlog 待触发）。

### 截图相对时间按上传当天换算（v0.15.0）

- **决定**：截图上的「3天前」等相对时间不再丢弃，保留原文并复用网页帖的 `resolvePublishedDate`，以 `exportedAt`（识别时刻，即上传当天）为基准换算；换算成功在状态区提示，失败保持不写日期的兜底。
- **理由**：截图 payload 的 `exportedAt` 就是识别时刻，天然是「上传当天」，不需要用户补拍摄日期。
- **否掉的方案**：沿用旧行为清空时间并提示无法换算。

### 发帖人写法统一带中文引号（v0.15.0）

- **决定**：单帖与合并提示词统一规定提及发帖人写作「平台名 + “平台用户” + 中文引号括起的 @昵称」，例如：小红书平台用户“@某某”；同时收紧补充说明写入标准（只在带来新事实、事件进展、处理结果或更正时写入）。
- **理由**：原表述「以平台用户“@用户名”引出」中的引号本是占位符，模型时取时舍，导致截图概括与单帖概括写法不一致；用户确认要带引号的写法。
- **否掉的方案**：保持占位符写法让模型自行取舍。

### 合并概括点名发帖人，评论只进观点区（v0.15.0 补充）

- **决定**：`MERGE_SYSTEM` 的 event_summary 规则明确：以首帖发帖人引出（写法同统一的带引号写法），后续帖文提供新信息、新进展或不同说法时同样写明其发帖人；评论区内容全部归纳到 opinion_points，正文不写「评论中……」。opinion_points 的篇幅与转述要求与单帖对齐（一句话、50 字内、归纳问题类型、规范书面语）。
- **理由**：合并概括此前会丢掉所有发帖人用户名——证据里带着 author，但提示词没有要求点名；评论内容混进正文也让合并简报与单帖格式不一致。
- **否掉的方案**：只改「提及帖文时统一写作」一句、不动 event_summary 字段规则——字段规则才是模型写 event_summary 的直接依据，不在字段规则里点名，丢用户名的问题不会消失。

## 2026-11-09

### 飞书推送等链接归位再发，已发送后标旧版本并可一键重发（v0.16.0）

- **决定**：生成期间用户补入的链接不再被飞书消息抢跑。后台在推送前向面板同步查询是否还有比本次 `givenUrl` 更新的待补链接；有就先记 `notification = { status: "deferred" }` 不推送，面板完成 relink 后用最终 `result.text` 调 `XHS_AI_NOTIFY_FEISHU_RESULT` 补发一次，一次生成仍只有一条消息。结果已经发送过之后再补链接、改清单链接或手工编辑，不自动补发第二条（webhook 无法改/撤消息），只在结果卡显示「飞书里仍是旧版本」+ 飞书图标红点，点图标用当前文本重发。每次成功推送记录 `notification.sentText`，作为“飞书里是不是旧版本”的判据；旧数据缺该字段时按无法判断处理。合并结果同规则。
- **理由**：用户实际痛点是飞书里留下长链、面板和历史却已是短链；重复消息又不可接受。把“唯一一条消息”推迟到文本最终确定之后，既不重复也不丢链接。
- **取代**：2026-10-28「补链接不调用模型、不重推飞书」中的「不重推飞书」部分——补链接仍然不自动重推（除非是生成中待补链接的延迟补偿），用户可显式重发；「不调用模型」仍然有效。
- **否掉的方案**：① 每次文本变化都自动补发第二条（webhook 不能改消息，飞书里会堆重复）；② 取消自动推送、全部改为手动（丢掉现有便利）；③ 维持现状（长链消息与实际结果不一致，且不提示）。

## 2026-11-15

### 涉事学校、单位要尽量从评论区线索查明全称（v0.16.3）

- **决定**：帖文只写「某高校」之类的代称或只写简称时，概括要综合正文、图片与评论区线索（含发帖人对网民追问的简短回复）尽量查明涉事主体的具体名称，并一律写全称。单帖与合并共用同一条规则 `SUBJECT_RULE`。
- **理由**：用户反馈的实例中，评论区追问「北工商还是首师」、发帖人回复「1」，已足以认定学校，概括却写成「未说明学校全称」。
- **分级写法**：发帖人已确认或证据足以认定时，标题和正文直接写全称；只有网民猜测、发帖人未确认时，标题和正文保留「某高校」等代称，猜测的具体名称写进 opinion_points。用户确认保留代称。
- **否掉的方案**：网民猜测也直接写进标题（错指学校的代价大于少写一个校名）。

### 线索足以认定时标题正文一致写全称并交代依据（v0.16.5）

- **决定**：发帖人未明说、但其透露的校区、学校类型等信息指向唯一主体，或与网民点名吻合且发帖人未否认时，视为足以认定：标题和正文都写全称，正文写「据发帖人所述……可认定为……」，不写「未明确确认」，也不能写成「发帖人确认」。
- **理由**：用户实测公费医疗帖时，标题已写北京中医药大学，正文却写「发帖人未明确确认」、观点区仍当猜测，前后矛盾；用户确认按标题口径统一。
- **否掉的方案**：维持「只有发帖人明确确认才写进正文」，标题与正文口径不一。

### 设置页模型默认共用一组，按需分开配置（v0.17.0）

- **决定**：设置页默认只有一组「API 地址、模型名称、API Key」（预填 DeepSeek 与 `deepseek-flash`），文字概括与图片识别共用；「文字与图片分开配置」开关打开后才填第二组。分开模式下图片 Key 留空时，只在两边 API 同域名时沿用文字 Key，不同域名必须单独填。「测试模型」会额外发一张内置小图确认能否看图，失败时提示并可一键改为分开配置。报错文案共用模式说「模型」，分开模式保留「文字模型 / 图片模型」。
- **理由**：多数模型同时支持文字与图片，默认填两遍 Key 是负担；跨域名沿用 Key 会把一家厂商的 Key 发给另一家；不能看图的模型要在测试时就暴露，而不是概括时静默跳过识图。
- **否掉的方案**：分开模式下图片 Key 无条件沿用文字 Key（跨域名泄露 Key）；只测文字连通（发现不了模型不支持图片）。

## 2026-11-16

### 长截图在暂存时自动切段（v0.18.0）

- **决定**：截图暂存时读取原始尺寸，高度超过宽度约 2.5 倍（或高度超过 8192 像素）时，按原分辨率自动切成带重叠的几段再交给图片模型；普通截图保持原样上传。宽度超过 8192 像素的图无法靠纵向切段解决，暂存时直接提示先缩小。段间重叠由截图提示词已有的「多张按顺序拼接、去掉重叠」规则处理，暂存缩略图显示段号；长截图的分段缩略图按整组移除，避免只删中间段导致内容缺失。切段后的张数计入后台单次 8 张上限，超出时提示先移除部分截图。
- **理由**：DeepSeek 等图片接口把「单边超过 8192 像素」报成 `unsupported image` 格式错误，用户实测长截图被拒收；而且图片模型推理前会把整张图缩到约 1300×1300 总像素，整张长截图即使不被拒收，文字也会被缩糊。用户确认按 backlog 的方案 B 自动切段。
- **否掉的方案**：只做上传前的尺寸预检、让用户自己切图（用户明确要自动）；把长截图整体降分辨率上传（v0.15.0 已否掉，会毁掉文字）；按 2.5 倍比例切但不设 8192 像素兜底（宽度超限的图仍会被接口拒收，高度超限的宽图也不切）；分段缩略图各自独立移除（会静默丢掉中间段）。

### 长截图在暂存区仍显示为一张，只标注自动切段（v0.18.1）

- **决定**：长截图自动切段后，暂存区仍按原截图显示一张缩略图，角标写「长图 · 4 段」，素材区提示识别时会自动切成几段上传；这张卡片的移除按钮作用于整张截图。按钮文案按原截图张数计（一张长图显示「识别这张截图并概括」），底层发送的仍是切段后的多张。
- **理由**：用户实测一条长截图上传后显示成四张独立缩略图，感觉别扭；切段应只是识别链路的内部处理，界面仍应保持「一张截图」的直觉。
- **否掉的方案**：把每段作为独立卡片显示（v0.18.0 的做法，用户反馈别扭）；只标段号「1/4」不说明是长图切段（用户看不出为什么变成四张）。

### 界面上的「清单」按用途改称「合并概括」，空时常驻窄提示（v0.18.2）

- **决定**：用户可见文案不再出现「清单」。区块标题改为「合并概括 · N 条」，当前帖文按钮「＋ 加入合并」、结果卡「加入合并」、截图「识别并加入合并」，该帖已在合并里时两处按钮都显示「✓ 已在合并里」并置灰；清空按钮改为「清空」。合并概括区为空时不再整块隐藏，收成一条窄提示「合并概括 · 0 条 / 同一事件的几条帖文（含截图）放进来，生成一份简报。」。代码内部（basket、`XHS_AI_MERGE_*`）不改名。
- **理由**：用户反馈「加入清单」抽象。「清单」只是容器，用户想不到它能合成一份简报；而且清单为空时整块隐藏，第一次点击前看不到东西会去哪。按用途命名，加上常驻的空状态，用户不用先理解「清单」是什么。「合并」与结果来源标签「合并 N 条」口径一致。
- **否掉的方案**：「一起概括」「多帖合并」等其他叫法；继续空时隐藏、只靠加入后的状态提示说明用途。

### 截图原帖链接挂到暂存卡上，贴入时询问归属（v0.19.0）

- **决定**：暂存区有截图时，往素材输入框贴小红书链接就立刻问「下面这组截图的原帖链接 / 另一条帖文，识别它」，选了前者才把链接挂到暂存卡的「原帖链接」一行（可移除）；提交截图只认挂着的链接，不再从输入框顺带读取。先贴链接后加截图同样会问；此状态下回车或点「识别链接」也先问。截图识别后（或识别中）才贴的链接，若对不上任何帖文而有没链接的截图条目，列出这些条目让用户选，不直接当新帖打开。仍只有一个素材输入框。
- **理由**：用户反馈原流程别扭：要先贴图、再把链接放进输入框、还不能点「识别链接」，最后点加入合并时链接才被顺带带上，界面上看不出链接跟着哪组截图；误点「识别链接」会把已删除的原帖当新帖打开成死页面。截图帖文没有帖子 ID，无法自动比对，只能让用户明确选，与「绝不猜」一致。
- **否掉的方案**：在暂存卡里另设一个链接输入框（违背 v0.13.0「只设一个添加素材输入框」）；保留从输入框隐式带入（看不见、易误操作）；给「识别链接」旁加「挂到截图上」按钮（多一步点击）。

### 识别并加入合并：截图立即变成「识别中」占位条目，多批并行（v0.19.0）

- **决定**：点「识别并加入合并」后，截图立刻从暂存区搬进合并概括，成为带转圈的「识别中…」条目（链接一并显示），暂存区马上空出来，可以接着提交下一批，几批同时识别；成功后原地换成正常条目，失败时条目变红并提供「重试 / 放回暂存区 / ✕ 丢弃」。识别中或失败的批次存在时，合并按钮置灰并提示原因。
- **理由**：用户点了按钮后暂存区和合并区都没变化，只有顶部任务条在动，以为没反应；而且原来一批识别中不能提交下一批，「一条一条加」的节奏要等。进度应出现在用户点的东西要去的地方。
- **否掉的方案**：只把按钮改成「识别中…」（不解决等待，也看不出东西去了哪）；占位条目直接写进后台清单（识别失败时要回滚，且合并会读到半成品）。

### 截图单次上限放宽到 20 张，单边 4096 由程序自动处理（v0.20.0）

- **决定**：截图单次识别上限（后台 `MAX_SCREENSHOT_IMAGES` 与面板 `SCREENSHOT_BATCH_LIMIT`）从 8 改为 20。切段规则保持「目标段高 = 宽 × 2.5」。DeepSeek 一次 15 张及以上时单边上限降到 4096，程序自己处理：切段每段控制在 4096 以内，段数封顶或宽度超出时等比缩小，不给用户提示。截图评论超过 50 条被截掉时也不提示。
- **理由**：8 张是 v0.4.0 定的保守值，不是接口限制（DeepSeek 单次 600 张）；一张评论多的长图就会切满 8 段，段被迫拉长、文字被模型缩糊。按宽度比例切能让不同分辨率手机截图在模型缩放后字号一致，用户主要用手机截图，所以不改。30 张被否：评论只用前 50 条，20 段已远超所需，更多段只会加大体积与输出长度。
- **否掉的方案**：上限 30（收益小、体积与截断风险大）；上限 14 以绕开 4096 规则；4096 超出时提示用户拆图或缩小；按固定像素切段；超过 50 条评论时提示未用上。
