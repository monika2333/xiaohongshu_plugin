# 决策日志

> 只追加，不改写。每条写明：日期、决定、理由、否掉的方案。只记录用户确认过的决定。
> 新的写在最下面。

## 早期（日期不详，2026-10 以前）

### 模型 Key 由用户自备

- **决定**：扩展不内置任何 API Key，用户在设置页填写自己的 OpenAI-compatible 接口。
- **理由**：商店合规；避免密钥泄露与费用风险。

### 图片识别与文字概括分开调用

- **决定**：图片模型只负责如实描述和 OCR；内容是否有增量、是否写进概括，由文字模型判断。
- **理由**：串行合并调用对图片多的帖文太慢；职责分开后两边提示词都更好控制。

### 提示词通过书面规则修正，不加示例

- **决定**：输出质量问题通过改写提示词里的规则解决，坚持最小干预、一次只改一处并单独测试。不新增 few-shot 示例，现有示例也考虑移除。
- **理由**：示例容易被模型照抄，让输出变得僵硬。

## 2026-10-28

### 侧边栏改为统一工作区（v0.13.0）

- **决定**：去掉「单条帖文概括 / 多条帖文概括」两个页签，改为「当前帖文 / 添加素材 / 清单 / 结果」四个区块。任何来源得到的帖文都是同一种素材，可以单独概括，也可以随时加入清单合并。
- **理由**：单条还是多条，是素材攒到最后才知道的，不该一开始就让用户选模式。原设计导致两个痛点：概括后补不进短链；已概括的帖文无法直接转入合并。
- **否掉的方案**：保留双页签、只在结果卡片上加「补链接」和「加入清单」。改动小，但界面「两套东西并排」的混乱感不会消失。

### 短链自动识别归位，为此新增 xhslink.cn 权限

- **决定**：只设一个「添加素材」输入框。贴入的链接先解析成帖子 ID，再与当前帖文、清单条目比对：对上了就补链接，对不上就作为新帖打开，解析失败就让用户手动选择，绝不猜。结果卡片和清单条目上的链接框保存时也会校验。
- **理由**：短链本身不含帖子 ID，只靠输入框位置区分意图，用户要自己贴对地方，贴错了插件无法察觉，错链接会直接写进简报。
- **否掉的方案**：按输入框位置区分「补链接」和「新帖」，不加权限。

### 只支持 xhslink.cn，不支持 xhslink.com

- **决定**：短链解析与权限只覆盖 `xhslink.cn`。
- **理由**：用户实际拿到的短链基本都是 `.cn`。

### 补链接不调用模型、不重推飞书

- **决定**：换链接时只改 `source.givenUrl`，用已有的结构化结果重新渲染，并同步历史；不重新推送飞书，状态行注明「未重新推送飞书」。
- **理由**：链接本来就是程序写入的，与模型输出无关；重推会在飞书里产生重复消息。

### 引入 AGENTS.md 与 .memory 任务记录体系

- **决定**：根目录放 `AGENTS.md` 规定 AI 的工作流程；`.memory/` 存放项目上下文、决策日志、待办和每个任务的记录。交付说明就写在任务记录里，不再在根目录建 `DELIVERY.md` 或 `docs/delivery/`。
- **理由**：实现工作交给不同的 AI 会话完成，需要一个随仓库走的长期记忆，避免每次重新摸索或推翻已有决定。
- **配套**：打包改为白名单脚本，确保这些文件不会进入扩展包。

### 补链接不覆盖结果框里的手工编辑（v0.14.4）

- **决定**：结果对象记录 `renderedText`；补链接时若 `text` 已被手工改过，只替换旧的来源后缀或旧链接，两者都找不到就保持用户文本、提示手动修改。历史仍保存程序重渲染的干净文本。
- **理由**：链接是程序写入的，用户改的是正文；整段重渲染会无提示地丢掉用户的编辑。
- **否掉的方案**：继续整段重渲染，只在界面上加“编辑会被覆盖”的警告。

### 打包白名单要有防漏测试

- **决定**：`tests/package.test.cjs` 从 manifest、页面引用、`importScripts` 和 `executeScript` 反查运行时文件，缺一个就让 `npm run check` 失败。
- **理由**：白名单靠人工维护，新增文件时漏加只会在打包后才暴露。

### 任务记录只记里程碑，微调合并归档（2026-10-29）

- **决定**：任务记录只为有分量的版本立档（新行为、新约定、新权限、成批修复）。纯样式或文案微调并入本次会话最近的任务记录，或与相邻小版本合并成一份档案，一个版本一行；被后续版本取代的中间方案（如同一图标多次重画）不留细节，最终形态以 `context.md` 约定和代码为准。
- **理由**：2026-10-28 一天产生 14 份记录，其中 10 份是界面微调，内容与 `context.md` 的约定重复；重新生成图标一个图标写了 4 份。任务记录的价值在决策与验收上下文，不在逐次改动本身。
- **整理**：v0.13.2–0.13.8、v0.14.1–0.14.3 十份合并为 `tasks/2026-10-28-v0.13.2-0.14.3-ui-polish.md`；完整保留 v0.13.0、0.13.1、0.14.0、0.14.4 四份。

### 平台徽标统一：小红书一律红色「小红书」，不再叫「网页」（v0.14.6）

- **决定**：所有出现平台徽标的位置（当前帖文、任务条、清单、历史列表），小红书固定显示「小红书」并用主题红（`merge-badge-xhs`）；微博橙、截图深红、合并黑不变。
- **理由**：历史列表里小红书条目曾显示绿色「网页」，与微博「微博」不对等；绿色也与产品主色冲突。用户确认统一为品牌红。
- **否掉的方案**：维持「网页」通称；为小红书另选配色。
