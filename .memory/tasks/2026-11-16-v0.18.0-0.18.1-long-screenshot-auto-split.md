- 需要用户在浏览器里手动验证：
  1. 加载扩展后，在「添加素材」里选择原长截图（1080 宽、高度数千像素），暂存区应只出现一张缩略图，角标写「长图 · 4 段」，素材区提示「识别时会自动切成 4 段上传」。
  2. 点「识别这张截图并概括」，状态区显示「共 1 张截图（自动切成 4 段）」，接口不再报 unsupported image；生成结果能读出正文与评论。

  4. 一次加入多张长截图导致切段后超过 8 段时，应提示先移除部分截图，且不发出识别请求。
  5. 长截图暂存卡片点 × 应移除整张截图（素材区提示「已移除整张长截图（N 段）」），而不是只删掉这一段，也不会在暂存区留下其他分段。

## 偏离委托的地方

- backlog 只写了「高度超过宽度约 2.5 倍」，本次额外加了「高度超过 8192 像素也切」的高度兜底，以及「宽度超过 8192 像素暂存时提示缩小」：只按比例可能漏掉宽图的超高情况，而图片接口有单边 8192 像素上限；切段目标高度也限制在 8192 以内。
- 切段后单张最多 8 段（与后台单次上限一致）。特别长的图在切 8 段后每段仍超过 8192 像素时，只在暂存阶段提示先用其他工具拆分，没有做「多批识别后合并 OCR 结果」，后者涉及跨请求合并，超出本次范围。
- 长截图暂存项按 `groupId` 整组移除，不能只删中间某段：分段是内部产物，单独删段会静默丢掉内容，用户如需删整张图可点任意一段的 ×。

## 遗留问题

- 切段后的每段计入后台单次 8 张上限：多张长图同时识别或单图需要 8 段以上时会受限制，已在暂存 / 提交时提示；如实际经常遇到，再考虑多批识别后合并 OCR 结果。已记入 `backlog.md`。
- 源文件超过 12 MB 的长截图在切段前就被体积检查拦下（提示压缩后重试），切段本可处理这类大图。大 PNG 长图实际少见；若遇到，把体积检查移到切段之后即可。已记入 `backlog.md`。
- 长 PNG 截图切段后本批 data URL 可能接近 32 MB 消息上限，届时会提示分批识别；触发时再考虑按体积把 PNG 段改为 JPEG。已记入 `backlog.md`。
- 截图识别仍按「一批截图来自同一条帖文」处理；同一批里放不同帖文的截图会被合并成一条，属于既有行为。用户这次的两张图是两条不同帖文，建议分别识别后加入清单再合并。

## 审核备注（仅当新增权限或数据流时）

本版本未新增权限、域名或数据流向。长截图切段只改变发往用户已配置的图片模型 API 的图片形态：普通截图仍以原始文件与格式发送；长截图在本地按原分辨率切成带重叠的多段并重新编码为 PNG / JPEG 后发送，不增加新的接收方，也不会保存截图二进制。
