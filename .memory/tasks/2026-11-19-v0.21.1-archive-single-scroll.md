# v0.21.1 小红书截图存档改为边加载评论边截图，页面只滚一遍

- 日期：2026-11-19
- 版本：manifest / package.json 均为 0.21.1
- 提交：见本次提交
- 委托：用户实测 v0.21.0 发现页面滚两遍（先加载评论、再截图），问能否同时进行。讨论了做法与代价（错位风险、不能切页签的时间变长、采集脚本与存档耦合）后，用户确认按「边加载边截、收尾核对错位并补截」实现。
- 关闭的 backlog 条目：无

## 改了什么

| 文件 | 改动 |
| --- | --- |
| `content-script.js` | 新增 `createArchiveFrameHook`：采集参数带 `archive` 时，加载评论前发 `XHS_ARCHIVE_FRAME` start，每滚一步并等过新评论后发 frame，`loadTopLevelComments` 的 finally 里在恢复滚动位置之前发 end；每步都等侧边栏回复，未获 ok 或超时（start 30 秒、frame 15 秒、end 90 秒）就停止请求，评论照常加载。找不到评论区时由 `runCapture` 补发 end。 |
| `archive.js` | `pageMeasure` 返回锚点（评论区顶部与前 80 条一级评论顶部，滚动内容坐标）。新增纯函数 `frameStillValid`（截图时位于该帧底边以上的锚点最后必须原地不动）与 `planCoverage`（每段取往下看得最远的帧，记录缺口）。新增 `liveStart`（滚到顶截初始屏兼作第一帧）、`liveFrame`（原地截一帧）、`liveFinish`（定评论区范围、丢错位帧、`captureLong` 补截缺口）、`composeCommentFiles`。 |
| `panel.js` | 新增 `handleArchiveFrame` / `runLiveCapturePhase`：只响应登记过的页签与 pageSessionId，start 时占住截图队列（`acquireCaptureSlot`），end 核对补截后先回复、再在侧边栏拼接；出错即 `failLiveCapture`，带回已截的初始屏。`handleArchiveReady` 有边加载边截的结果就直接用，否则（微博、未能启动）照旧单独滚一遍。采集失败时 `finalizeArchiveForTab` 一并关闭会话。 |
| `tests/archive.test.cjs` | `frameStillValid` 各情形、`planCoverage` 段与缺口；`liveFinish`：一帧错位只补截那一屏、全部有效时不补截；侧边栏端到端：start → frame ×2 → end 全部 ok，别的页签的请求不响应，不再单独滚一遍，存档 5 个文件、关联历史、提示条收起。 |
| `tests/content-script.test.cjs` | 存档开启时消息顺序为 start → frame… → end，end 时尚未恢复滚动位置，截图信号在其后；侧边栏不接时只发 start、评论照常；未开启时不发截图请求。 |
| `tests/service-worker.test.cjs` | 版本断言 0.21.1。 |
| `README.md` | 说明小红书边加载边截、错位自动补截，微博仍单独滚一遍。 |

## 实测与验证

- `npm run check`：通过。
- 需要用户在浏览器里验证：
  1. 小红书帖文点「提取并概括」，页面应只滚一遍；红色提示条依次显示「正在截取帖文初始屏」「正在边加载评论边截图（第 N 屏）」，偶尔出现「正在补截评论区」属正常。
  2. 评论区长截图有无拼缝、重复或空白。
  3. 加载评论过程中切走页签：截图应立即停止，评论照常加载完成；结果卡出现「重新截图」。
  4. 微博帖文仍是加载完再单独滚一遍截图。
