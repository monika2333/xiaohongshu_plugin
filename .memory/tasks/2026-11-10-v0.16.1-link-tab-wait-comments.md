# v0.16.1 链接概括新页签等待互动数与评论就绪

- 日期：2026-11-10
- 版本：manifest / package.json 均为 0.16.1
- 提交：分支 `fix/link-open-missing-comments` 的 HEAD（工作树 `.worktrees/link-comment-bug`）
- 委托：用户口头排查「贴链接跳转过去之后只读取了贴文原文，评论和点赞（数据与内容）都没有读取，就直接生成概括发到飞书」。
- 关闭的 backlog 条目：无

## 根因

链接概括流（`panel.js` 的 `runLinkWorkflow` → `waitLinkTabPage`）只要帖文详情 DOM 里的标题/正文渲染出来（`XHS_PAGE_CONTEXT` 的 `detailReady`）就开始采集。小红书帖文页是 SPA，标题与正文先渲染，互动条（点赞/收藏/评论数）和评论列表要等后续挂载与评论接口返回，于是采集发生得太早：

1. `content-script.js` 的 `loadTopLevelComments` 在 `.note-scroller` 未挂载时立即返回 `{ loaded: 0, reason: "comment_scroller_missing" }`，一条评论都不等。
2. 滚动循环里，0 条评论且容器不可滚动时约 4 秒（4 个稳定轮次）就判 `page_exhausted`——这套语义是为「页面已加载完」的手动场景设计的，把「还没加载出来」当成了「没有」。
3. `extractNote` 在同一时刻读互动数，读到空值。下游 `renderSummary`（`ai-pipeline.js`）对空互动数静默省略「获 X 次点赞、Y 条评论」整句，证据里 0 条评论，模型写不出观点——飞书简报只剩正文概括。

手动提取不受影响（用户点按钮时页面早已加载完）；微博不受影响（走页面同源 `/ajax/` 接口取数，不依赖 DOM）。

## 实测与验证

- `npm run check`：通过（语法检查 + 9 个测试脚本 + 打包白名单防漏，全部绿）。
- 单元测试覆盖不到、需要用户在真实浏览器里手动验证的步骤：
  1. 贴小红书帖文短链（或分享文案里的链接）触发链接概括：结果应包含点赞数、评论数句式「截至目前，该帖文获 X 次点赞、Y 条评论。」与评论观点，与手动提取结果一致。
  2. 网络较慢时贴链接：任务条应先显示「正在等待页面就绪」，随后正常生成，不超时不报错。
  3. 手动在帖文页点「提取并概括」与「加入清单」：行为不变（页面已加载完时新增等待不产生额外延迟）。
  4. 找一个确实没有评论的帖子概括：应很快完成（不空等），结果无「评论未能读取」提示。
  5. 微博链接概括：行为不变。

## 偏离委托的地方

- 委托只要求排查原因；修复方案（采集端等待就绪而非面板端加强 `detailReady` 门控）由本次实现选择，理由：手动提取快速点击时同样受益，且面板轮询协议与测试无需改动。
