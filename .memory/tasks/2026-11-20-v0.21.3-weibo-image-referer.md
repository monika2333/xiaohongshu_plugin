# v0.21.3 修微博配图下载与识别被图床防盗链挡住的 403

- 日期：2026-11-20
- 版本：manifest / package.json 均为 0.21.3
- 提交：见本次提交
- 委托：用户反馈微博帖文（`https://weibo.com/1257000310/5342270053944877`）截图存档提示「1 张配图下载失败」，重试仍失败，问是自己代码的问题还是一次意外。
- 关闭的 backlog 条目：无

## 原因

是代码的问题，而且所有微博配图都受影响，不是这一次的偶发。证据链：

1. 用户桌面存档目录 `薯页摘录-截图存档/2026-11-20_123221_微博_百忍说_Dvgyf3` 的 `采集数据.json` 里有唯一一张配图：`https://wx3.sinaimg.cn/large/4aec4d76ly1ih0ock070wj20nx0tngp0.jpg`；同帖重试生成的第二个文件夹同样没有 `配图-*.jpg`，而四个小红书存档都有 `配图-01.webp`。说明失败的是微博图床这一类请求，不是某一张图。
2. 用浏览器 UA 直接请求该图：不带 `Referer` 返回 403（238 字节的拦截页），带 `https://weibo.com/` 的 `Referer` 返回 200（135664 字节 JPEG）；换 `example.com` 的 Referer 仍 403，`*.sinaimg.cn` 各路径版本行为一致。图床按「浏览器 UA + 必须有 weibo.com 来源」做防盗链。
3. 用用户 Edge 配置副本加载商店版 0.21.2（即本仓库 HEAD 的代码），在扩展页面里实测：`fetch` 该图返回 403；`fetch(..., { referrer: "https://weibo.com/" })`、`referrerPolicy: "unsafe-url"` 都还是 403；抓包看扩展页面发出的请求既没有 `Referer`，`XHR.setRequestHeader("Referer", ...)` 也被浏览器丢掉。Chromium/MV3 不会给扩展页面发出的请求带 Referer，也禁止脚本自行补。
4. 同一套取图代码也用于概括前的图片识别（`ai-pipeline.js` 的 `imageToDataUrl`）。`resolveVision` 捕获异常后只把进度写成「图片识别未完成，继续概括文字内容」，所以用户那条微博的概括只用了文字，界面上看不出图片识别也失败了。

## 实测与验证

- `npm run check`：通过（打包白名单已覆盖新增的 `media-access.js`）。
- 两个「先注册规则再取图」的用例做了变异验证：把 `archive.js` / `ai-pipeline.js` 里的 `await` 改成 `void` 后，对应测试分别失败（`archive mutation exit=1`、`ai-pipeline mutation exit=1`），恢复后通过。
- 用 Playwright 自带的 Chromium 140 以 unpacked 方式加载本仓库改后版本，在真实扩展页面里验证：
  - `chrome.permissions.getAll()` 含 `declarativeNetRequestWithHostAccess`；
  - 用出问题那条微博的 payload 调 `XhsArchive.collectMediaFiles`：`failed: 0`，生成 `配图-01.jpg`，135664 字节 `image/jpeg`（修复前是 403）；
  - 动态规则已注册，条件为 `requestDomains: ["sinaimg.cn"]`、`resourceTypes: ["xmlhttprequest"]`、`initiatorDomains: [扩展 ID]`；
  - 后台 Service Worker 上下文里直接 `fetch` 同一张图也返回 200 / 135664 字节，说明 `initiatorDomains` 用扩展 ID 同样覆盖后台请求（图片识别走这里）。
- 受限于 Edge 商店版仍是 0.21.2，无法在用户现在这套 Edge 上直接跑改后的代码；需要用户重新加载扩展（或等商店更新到 0.21.3）后复验。复验步骤：
  1. 重新加载扩展，打开那条微博，确认「提取并概括」可以正常完成。
  2. 开启截图存档再提取一次：结果卡不再出现「1 张配图下载失败」，文件夹里出现 `配图-01.jpg`。
  3. 换一条配图有文字内容的微博：概括里应能写出配图内容（此前图片识别静默失败，只按文字概括）。
- 权限提示：Chrome 官方权限列表里 `declarativeNetRequestWithHostAccess` 没有用户可见警告，只有 `declarativeNetRequest` 会显示「Block content on any page」；本次只新增前者，安装时的权限提示不变。

## 审核备注（新增权限 `declarativeNetRequestWithHostAccess`）

本版本新增 `declarativeNetRequestWithHostAccess` 权限，用于修复微博配图无法下载/识别的问题。微博图片服务器要求请求带微博站点来源（Referer），否则一律返回 403；扩展页面与后台程序发出的请求本身不带 Referer，也无法通过脚本补上。扩展因此登记一条请求头规则，只给**扩展自己发出**的、指向 `*.sinaimg.cn` 的图片请求补上 `Referer: https://weibo.com/`；规则用 `initiatorDomains` 限定为扩展自身，不改动用户网页发出的请求，也不影响其他网站。该权限只依赖扩展安装时已声明的 `*.sinaimg.cn` 主机权限，不新增安装时的用户可见权限提示；不产生新的数据收集或传输。

This release adds the `declarativeNetRequestWithHostAccess` permission to fix Weibo images failing to download or be recognized. Weibo's image CDN (sinaimg.cn) rejects requests without a Weibo site Referer with HTTP 403. Requests issued by extension pages and the background worker carry no Referer, and scripts cannot set one. The extension therefore registers a single header-modification rule that sets `Referer: https://weibo.com/` only for image requests to `*.sinaimg.cn` that the extension itself makes; the rule is scoped to the extension as initiator, so requests made by the user's web pages are untouched. It relies only on the `*.sinaimg.cn` host permission already declared at install time, adds no new install-time permission prompt, and introduces no new data collection or transmission.
