## 验收返修（2026-11-09）

1. **多窗口查询应答**：`answerPendingLinkQuery` 改为「有 pending 先答 true（属主已切走也答），无 pending 只有 `activeTabId === tabId` 才答 false，其它情况不响应」。补 panel 用例：非属主页签无 pending 不响应；属主切到别的页签但 pending 仍在仍答 true；属主当前页签且无 pending 答 false。
2. **慢补发竞态**：`finalizeDeferredFeishu` 在 await 后按 `historyId` 找回 `slot.result` / `mergeSlot.result` 的**当前**对象，把 notification 写到当前对象并渲染；新增 `feishuNotifyInFlight`（按 historyId）在途集合，补发期间手动点图标只提示「正在推送飞书，请稍候」、不发第二条；`keepLocalSent` 保留，覆盖广播晚于补发完成的情况。补 panel 用例：NOTIFY 返回 pending promise，等待期间投递同 historyId 的 relink 工作流广播，再 resolve，断言结果卡为 sent、提示隐藏、状态一致，且等待期间点图标未发 `XHS_AI_SEND_FEISHU`。
3. **状态标题回归**：`finalizeDeferredFeishu` 增加 `title` 参数；`runFullWorkflow` 传「概括完成」，`regenerateActiveTab` 传「重新生成完成」，`runMergeSummarize` 按 `force` 传「重新生成完成 / 合并概括完成」；panel 用例同步改为断言「重新生成完成」。
4. **手动发送 deferred 结果**：发送成功后若结果仍对应当前焦点且状态为 done，状态行 detail 改为「已推送到飞书。」，标题不变（历史屏不改）；补 panel 用例（模拟面板重开后 deferred → 点图标 → 状态行更新、提示消失）。

## 实测与验证

- `npm run check`：通过（9 个测试脚本 + 语法检查 + 打包白名单防漏，全部绿）。
- 基线检查的一个既有问题：`tests/service-worker.test.cjs` 的 vm context 没有注入 `Date`，v0.15.0 的「截图相对时间按上传当天换算」用例里 `fixedNow` 是 Node realm 的 Date，`instanceof Date` 恒为 false，测试实际取当天日期。2026-11-09 跑基线即失败（期望 10-26、实际 11-06）。本次给测试上下文补 `Date` 使既有断言恢复确定性，不改变产品代码。
- 单元测试覆盖不到、需要用户在真实浏览器里手动验证的步骤：
  1. 未配置飞书：结果卡不显示飞书图标和旧版本提示。
  2. 帖文页点「提取并概括」，任务进行中贴同一帖短链：完成后飞书只收到一条短链消息；面板、历史、飞书文本一致；状态行显示「链接已更新，并已推送到飞书。」。
  3. 先贴短链、再点提取：生成时已带短链，飞书直接一条短链消息，不出现延迟补发。
  4. 已推送后补链接：不自动重发；结果卡出现「飞书里仍是旧版本，点飞书图标重发当前内容。」与图标红点；点图标后飞书收到当前文本，提示与红点消失；历史条目同步。
  5. 直接编辑结果框：提示随输入出现，改回已发送文本消失；再次发送后 `sentText` 与当前文本一致（可在历史/重开后确认）。
  6. 合并两条帖文，运行中改清单条目链接：合并完成后只收到一条含新链接的消息；已发送后再改链接或编辑，出现旧版本提示并可点图标重发。
  7. 先贴链接、还没提取（含清单采集进行中）：反馈为「已记下链接，提取时会带入。」；随后提取仍带该链接。
  8. 多窗口各开一个侧边栏：后台查询只由拥有该页签/合并任务的面板响应，不应互相抢答。
  9. 升级后用 0.15.0 产生的历史查看：不报错、不显示旧版本标记（旧数据无 `sentText`）。
  10. 网络较慢时延迟补发期间点飞书图标：只提示「正在推送飞书，请稍候」，飞书不会收到第二条；补发完成后提示消失。

## 偏离委托的地方

1. `finalizeDeferredFeishu(target)` 增加了可选的 `{ tabId, relinked, title }` 参数：`tabId` 用于页签在等待期间被切换时仍写回正确槽位；`relinked` 决定「链接已更新，并已推送」还是「概括已生成，并已推送」；`title` 让 `regenerateActiveTab` 保持「重新生成完成」而不被统一写成「概括完成」。行为与委托一致。
2. 截图帖文在页签管线里也排除了延迟推送（`source.origin === "user_screenshot"` 时不查询面板），不只是 `XHS_AI_SUMMARIZE`。原因：截图结果的链接在创建时已确定，若重新生成截图时页签槽位恰好暂存了别的链接，延迟后没有面板补偿路径，会永久停在 deferred。
3. `rerenderMergeIfPossible` 的返回值从字符串改为 `{ linkApplied, unchanged }`（内部函数，调用点已同步）：委托 2.3.3 需要区分 `unchanged` 以显示「合并条目已变化」提示，原返回值拿不到这个信息。
4. 面板把 `XHS_AI_QUERY_PENDING_LINK` 的同步应答合并进现有 `chrome.runtime.onMessage` 监听器，而不是新增第二个监听器；行为相同，并且避免测试 mock 只保留最后一个监听器。该分支同样是同步 `sendResponse` 后返回 `false`。
5. 手动发送图标仍走 `XHS_AI_SEND_FEISHU`（按委托 3.3 扩展为带上下文并记录 `sentText`），`XHS_AI_NOTIFY_FEISHU_RESULT` 只用于延迟补偿。两者都会更新历史与工作流快照，分工符合委托 3.2/3.3。
6. 测试侧修正：`tests/service-worker.test.cjs` 的 vm context 补 `Date`（见上节），否则基线用例本身无法通过；没有删除或弱化任何覆盖点。
7. 多窗口查询应答按「有 pending 先答 true、无 pending 只有 `activeTabId === tabId` 才答 false」实现（验收返修要求）。属主切走且没有 pending 时，后台没有面板应答，最多等 1500ms 超时后照旧立即推送——这是避免非属主抢答 false 的既定取舍，已写进 backlog 之外的实现说明。
8. 延迟补发的在途保护按 `historyId` 记录；旧数据没有 `historyId` 时用结果对象本身作键，面板重开后对象不同则识别不到，属于旧数据边界（已记入 backlog 的 `sentText` 兼容条目一并考虑）。
9. 手动发送成功后把当前焦点的状态行 detail 改为「已推送到飞书。」，只在结果仍对应当前焦点且状态为 `done` 时生效；标题保持不变，历史屏不改。
