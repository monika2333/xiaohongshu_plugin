# v0.21.4 修设置页「测试模型」的内置测试图损坏

- 日期：2026-11-20
- 版本：manifest / package.json 均为 0.21.4
- 提交：见本次提交
- 委托：用户填好 DeepSeek API Key 后点「测试模型」，提示「文字可用，图片识别失败：模型请求失败：… You have uploaded an invalid image. The image data is corrupted or truncated and could not be decoded.」；正常使用（真实帖文配图）不受影响，问测试功能是不是有问题。
- 关闭的 backlog 条目：无

## 原因

是代码的问题，出在 `ai-pipeline.js` 的 `VISION_TEST_IMAGE`：这串内嵌 base64 自 v0.17.0 引入起就不是有效的 PNG，与用户填的 Key、模型、正常图片识别都无关。

1. 把 `VISION_TEST_IMAGE` 解码后（108 字节）逐块解析：IHDR 正常，但 IDAT 声明长度 42 字节、`zlib.inflateSync` 报 `unexpected end of file`；IDAT 之后的 9 个字节不是合法 chunk（按 4 字节长度读出一个 9582176 字节的假 chunk），IEND 也不在正确位置。也就是说这串 base64 是一段伪造/截断的 PNG，不是编码时丢字符。
2. DeepSeek 图像接口按文件实际内容判断格式并做解码校验（[官方文档](https://api-docs.deepseek.com/zh-cn/guides/vision.md)：格式由内容判断而非文件名或 MIME），遇到坏图就在请求校验阶段返回用户看到的 `invalid image`；`ai-pipeline.js` 的 `callChat` 原样透出接口报错，所以文案里带着 `.messages[0].content[0]`。
3. 正常概括用的图片是采集到的真实截图/配图，走的是同一套 data URL 上传但内容有效，因此用户「正常使用没问题」，只有测试这一步失败。v0.17.0 引入后该字符串再没被改过（`git log -G` 只命中引入提交），所以这是从 v0.17.0 起就存在的回归，不是最近改坏的。

## 改了什么

| 文件 | 改动 |
| --- | --- |
| `ai-pipeline.js` | `VISION_TEST_IMAGE` 换成用 Pillow 生成并复核过的有效 32×32 纯红 RGB PNG（97 字节，data URL 132 字符）；注释说明测试会真解码校验、不要再手改 base64。 |
| `tests/service-worker.test.cjs` | 新用例：从 `testProvider("shared")` 实际发出的 vision 请求里取 data URL，按 PNG 规范校验签名、逐 chunk 长度与 CRC32、`zlib.inflateSync`、反过滤像素，断言 32×32、8 位 RGB、1024 个像素全是纯红；旧坏图会在第一个失败点（IDAT CRC）报错。版本断言改为 0.21.4。 |
| `manifest.json` / `package.json` | 版本 0.21.4。 |

## 实测与验证

- `npm run check`：通过（新增用例含在 `service-worker.test.cjs` 里）。
- 变异验证：把 `VISION_TEST_IMAGE` 换回 v0.17.0 的坏图后单跑 `node tests/service-worker.test.cjs`，按预期失败（`内置测试图 PNG chunk IDAT 的 CRC 不对`）；恢复后通过，确认新用例真能拦住同类回归。
- 用 Pillow 独立解码从 `ai-pipeline.js` 里提取的 data URL：`PNG (32, 32) RGB`，`getcolors()` 只有 `[(1024, (255, 0, 0))]`，即 1024 个像素全为纯红。
- 体积：97 字节，远低于 DeepSeek 单图 32 MiB 上限；官方文档写明总像素小于约 544×544 的图片会被等比放大，32×32 不需要改大。
- 仓库里不存用户 Key，无法在本地直接调 DeepSeek 复验。需要用户重新加载扩展后再点一次「测试模型」，预期显示「连接成功 · 文字与图片均可用（红色）」（括号内为模型对测试图的回答）。真实帖文配图的识别链路本次未改动。

## 偏离委托的地方

- 用户只是问测试功能是否有问题，本次除修好内置图外，补了会解码校验内置图的单元测试：这类「伪造 base64」无法靠肉眼发现，从 v0.17.0 一直漏到用户反馈，需要测试兜住。

## 遗留问题

- 现有 backlog 条目「图片连通测试按「红 / red」判断」仍然有效：本次只修图本身，没有放宽判定；若模型答「赤色」等说法仍会误判。
- 未新增 backlog 条目：32×32 对极少数可能有最小尺寸要求的 OpenAI-compatible 接口是否够用，DeepSeek 文档没有最小值限制（小于约 544×544 会放大），等实际用户反馈再处理。
